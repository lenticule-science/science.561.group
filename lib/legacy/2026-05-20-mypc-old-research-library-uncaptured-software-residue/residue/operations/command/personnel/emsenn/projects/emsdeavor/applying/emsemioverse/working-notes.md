## What I have learned from reading the corpus

### The runbook formalism (from Untitled 26.md §9, Untitled 20.md §5)

A **runbook** is a finite, linear YAML sequence of operator invocations.
No branching, conditionals, loops, or hidden state. A runbook is a
composite arrow in the free category generated by operator families.

The formal schema for programs (from Untitled 20.md §5.0):

```
Program:
  id:    ProgramID
  steps: list[ProgramStep]

ProgramStep:
  index:        int
  operator:     OperatorName
  input_nodes:  list[NodeID]
  output_kinds: list[NodeKind]
```

Programs are specified using ProgramSpec:

```
ProgramSpec:
  name:          ProgramName
  inputs:        list of logical inputs
  outputs:       list of logical outputs
  preconditions: predicates over MachineState and inputs
  postconditions:predicates over MachineState and outputs
  step_schema:   ordered list of abstract stages
```

**Carriers** are canonical JSON objects encoding mathematical structures.
Content-addressed via SHA256. Each has structural data, schema metadata,
and law-evidence objects.

**Realizers** are Python modules implementing operator kernels. Pure
functions: read carriers, construct new canonical carrier, insert into
graph. No mutation, caching, or ephemeral state.

**Operator implementations** are pure functions:
`impl_operator(input_payloads, MachineState) -> (outputs, edge_descriptions)`

### How runbooks map to skills (from parametric-runtime.md)

The key insight from parametric-runtime.md:

> "YAML runbooks under `runbooks/library/` wire acts into concrete
> simulations. Runbooks are the only place subsystems compose."

This means: skills ARE runbooks (or should be). A SKILL.md's operational
content should be a typed morphism — a finite sequence of operators with
typed inputs and outputs. The SKILL.md frontmatter already has `inputs:`
and `outputs:` fields. The `runtime:` field distinguishes `script` (has
a realizer) from `inference` (requires LLM).

### The gap between current skills and the formalism

Current SKILL.md files are prose instructions for an LLM agent. The
runbook formalism says they should be typed morphisms — finite linear
sequences of operator invocations, each with typed carriers in and out.

The bridge: a skill with `runtime: script` whose script IS a realizer
(pure function, canonical input/output) is already close to the formalism.
A skill with `runtime: inference` is an LLM-mediated operator — it takes
carriers as input and produces carriers as output, but the kernel is
inference rather than deterministic computation.

The skill manifest's `inputs:` and `outputs:` fields map to the
ProgramSpec's `inputs:` and `outputs:`. The `region:` field is a
(coarse) precondition. What's missing from the current manifest schema:
- `preconditions:` (predicates that must hold before execution)
- `postconditions:` (predicates that must hold after execution)
- `step_schema:` (ordered list of operators/stages)

### What this means for better-emsemioverse

The better-emsemioverse skill currently has:
- A SKILL.md with manifest frontmatter and prose instructions
- An assess.py script that produces a gap report

What it should have, per the formalism:
- A ProgramSpec-like structure in its frontmatter or body defining:
  - preconditions (repository exists, content/ exists, etc.)
  - postconditions (gap count decreased, or method improved)
  - step_schema: the ordered sequence of operations
- The assess.py script IS a realizer — it takes the repository state as
  input carrier and produces a gap report as output carrier

## Task: Unify skill frontmatter schemas

### The problem

There are at least two different frontmatter schemas in use for SKILL.md
files, and they contradict each other.

**Schema A — the formal spec.** The skill-manifests spec at
`content/technology/specifications/agential-semioverse-repository/theory/skill-manifests.md`
defines a manifest tuple with these fields: `id`, `name`, `version`,
`kind`, `runtime`, `inputs`, `outputs`, `region`, `dependencies`,
`scopes`. The `write-learn-skill` template at
`content/education/disciplines/pedagogy/skills/write-learn-skill/SKILL.md`
uses this schema in its own frontmatter (it has `id`, `version`, `kind`,
`runtime`, `triggers`, `inputs`, `outputs`, `region`, `dependencies`,
`scopes`).

**Schema B — learn skills and newer content skills.** The learn skill
template (the output format defined inside `write-learn-skill/SKILL.md`)
tells agents to generate skills with: `name`, `description`, `kind: skill`,
`skill-kind: learning`, `date-created`, `tags`. No `id`, no `version`, no
`runtime`, no `region`, no `inputs`/`outputs`, no `scopes`.

Some content skills (e.g. `writing-cosmology-content`) follow schema B:
`name`, `description`, `kind: skill`, `skill-kind: writing`,
`date-created`, `tags`.

There is also a third variant on older Codex-generated skills (e.g.
`learn-about-minnesota-environmental-review`) that adds `license`,
`compatibility`, `metadata`, `allowed-tools`, `summary`, and uses
`runtime` as a nested object with `invocation` and `tool` subfields.
These should be treated as stubs to overwrite, per the write-learn-skill
instructions.

### What emsenn prefers

- **`name` over `id`** — `name` is the human-readable label; `id` in the
  formal spec is described as "unique, immutable identifier" but in
  practice the directory name already serves that role (Remark 8.5 of the
  spec says "the skill's directory name serves as the id"). Having both
  `id` and `name` is redundant when directory names are the canonical
  identifier.
- **`kind` over `type`** — the formal spec already uses `kind` (with
  values `operational`, `learn`, `meta`). Schema B also uses `kind` but
  with the value `skill`, which is not in the spec's enum. The `type`
  field appears in some learn skills but is not in the formal spec at all.

### What needs investigation

These fields exist in the formal spec but emsenn does not know what they
are for. Before deciding whether to keep them, an agent needs to
determine what role each plays and whether the vault actually uses it:

- **`region`** — Defined in skill-manifests.md Section 3 as a read/write
  directory declaration for parallelism analysis. It lets a scheduler
  determine which skills can run concurrently. The question is whether
  this vault has or will have a scheduler that uses this, or whether
  region is premature formalism that can be deferred.
- **`runtime`** — Defined in skill-manifests.md Section 2 as the
  execution mode: `manual`, `inference`, `script`, or `documentation`.
  This tells the scheduler HOW to invoke the skill. The question is
  whether the current distinction between inference-driven skills and
  script-driven skills justifies a frontmatter field, or whether the
  presence of a script in the skill's directory is sufficient signal.
- **`skill-kind`** — Not in the formal spec at all. Appears in schema B
  as a sub-classification (values seen: `learning`, `writing`). This
  seems to be a finer-grained `kind` that emerged in practice without
  being formalized. The question is whether it should be folded into
  `kind` (expanding the enum) or dropped.

### What a unified schema might need to address

This is not a solution — just a list of tensions that unification must
resolve:

1. The formal spec has `id` + `name`. Practice uses only `name`.
   Directory-name-as-id (Remark 8.5) suggests `id` is derivable and
   does not belong in frontmatter.
2. The formal spec has `kind` with values `{operational, learn, meta}`.
   Practice has `kind: skill` with `skill-kind` for sub-classification.
   These need to be reconciled.
3. The formal spec requires `version`, `inputs`, `outputs`. Learn skills
   omit all three. Either learn skills are a different thing from
   operational skills (and the manifest spec does not apply to them), or
   learn skills should have manifest fields too.
4. `runtime`, `region`, `dependencies`, `scopes` are in the formal spec
   but absent from most actual skills. Either the spec is ahead of
   practice (and skills should be updated to include them) or the spec
   over-specifies (and these should be optional/deferrable).
5. `date-created` and `tags` are in practice but not in the manifest
   spec. These are standard vault frontmatter fields, not manifest
   fields — but the question is whether the manifest spec should
   acknowledge their coexistence.

### Why this will spiral (and that is fine)

Unifying the schemas will force decisions about what a skill IS in this
vault — whether learn skills are a kind of manifest entry or a separate
thing, whether the formal scheduler machinery (regions, runtimes,
scopes) belongs in frontmatter now or later, and how the spec and
practice should converge. That is schema work for the emsemioverse as a
whole, not just a frontmatter cleanup. The spiral is intentional.
