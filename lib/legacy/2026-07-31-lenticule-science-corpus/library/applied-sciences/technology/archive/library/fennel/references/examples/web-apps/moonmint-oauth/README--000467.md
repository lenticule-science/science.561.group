# Fennel web app example

An example of how to make a capabilities-based Fennel web app with
[moonmint](https://github.com/bakpakin/moonmint) that uses oauth for login.

The demo will allow you to log in, and when logged in, you can see a
list of other users who are also logged in. But you can extend it to
do whatever other things you want in your own web app.

This code is adapted from [fedibot.club](https://fedibot.club) and
[technomancy search](https://search.technomancy.us) which were the
first Fennel moonmint web apps deployed.

The basic skeleton including login takes under 250 lines of code. The
server consumes 16 MB of memory when running with the Fennel compiler
loaded at runtime or 12 MB of memory when using AOT compilation and
omitting the production repl.

## Features

* [capabilities system](https://conf.fennel-lang.org/2022#video2) (sandboxing)
* live reloading with repl
* oauth logins from fediverse servers
* [https client](https://github.com/love2d/lua-https)
* browser caching for static files
* starter CSS and robots.txt
* HTML generated from native Fennel data structures

Not included:

* database
* streaming https responses (needs a different HTTPS client)

## Usage

The only external dependency is [luv](https://github.com/luvit/luv).
Run `sudo apt install lua-luv` on Debian-based systems or the
appropriate command for your preferred package manager.

Running `make runloop` will start an HTTP server without TLS.  Put it
behind a reverse proxy like [Caddy](https://caddyserver.com/) for
that.

Use this repository as a starting point, and add your own logic
in. You can put your own handlers in a new file and require it from
`main.fnl` and add routes that reference it to the bottom of `main.fnl`.
Use the handlers in `responses.fnl` as an example.

Since there is no database, the login sessions will all be lost when
the server is restarted. Rewrite the `logins` table in `responses.fnl`
to use a database or filesystem!

Most code to be added should have the capabilities system applied to
it, since that will make it more secure and organized. Any module
required from `main.fnl` *after* `_ENV` is set will have this. The
main exception where you can't do this is if you have a library that
either assumes direct access to disk, or has to load a C module. For
such cases, require them near the top of `main.fnl` but be aware that
vulnerabilities in that code will be much more serious than problems
in the capabilities-based code.

During development you can run `make runloop` as your repl command in
your text editor; for instance with Emacs run `C-u M-x fennel-repl
RET make runloop RET`. You can reload most modules with `,reload responses`
etc but changes to `main.fnl` will require you to exit the repl and allow
the runloop to restart it.

## FAQ

* *Q*: What is this capabilities system stuff you keep going on about?
* *A*: Writing [capabilities-based code](https://justinpombrio.net/2021/12/26/preventing-log4j-with-capabilities.html)
  means making it so that the ability for a function to affect the
  outside world is represented as a value in your program that gets
  passed from one function to another instead of the implicit
  assumption that every function in the program might affect the
  outside world. It's a fantastically useful tool that improves
  security and code organization. See this [fennelconf
  talk](https://conf.fennel-lang.org/2022#video2) for more details.

* *Q*: Why not Openresty?
* *A*: My goal is to make it easy to install and administer with the
  fewest external dependencies outside apt-get. Openresty is a more
  developed ecosystem but it requires manual installation.

* *Q*: Why doesn't moonmint just do all this stuff by default?
* *A*: Well, yeah, it probably should, huh? But I don't want to
  maintain a whole dang web framework right now!

* *Q*: What HTTP client should I use?
* *A*: This includes the love2d one, which is very nice but doesn't
  support streaming responses. If you need that, you might try
  [lua-http](https://daurnimator.github.io/lua-http) instead, but its
  API is not nearly as nice. You can see an example of how to use it
  [from fedibot.club](https://git.sr.ht/~technomancy/fedibot-club/tree/main/item/request.fnl).

## Fediverse-specific OAuth flow

The first step of the *standard* OAuth2 flow is for the developer of the app
in question (that's you!) to sign up for an account on every single identity
provider that the app wants to support, and register a client with each of them.

If your goal is to support login thru one of a handful of abusive tech
monopolists, this is fine. But like... come on; that's dystopian and
utterly dreadful. We can do better.

The [Mastodon API](https://docs.joinmastodon.org/client/token/#app) as well
as other implementations that support it (like GotoSocial) will let you
register a client automatically. But it means our flow we use here is
different (read: better, but more steps) than "normal OAuth".

This isn't really an ActivityPub thing; it depends on Mastodon's API, but
since there are a bunch of great Fediverse clients like Tusky and Pinafore
that use it, most AP servers will support it rather than have to build out
their own clients from scratch.

Anyway here we go; five easy steps you can do in about a hundred lines of code.

Step 1: ask the user *where* they want to log in. This is the `login`
function in `responses.fnl`; its job is to render an HTML form with only one
field: `instance`.

Step 2: once we have an instance, register a client by posting to
`/api/v1/apps` with the fields `client_name`, `website`, `redirect_uris`, and
`scopes`. The first vary based on your app, but `scopes` should just be the
string `"profile"` as long as all you're trying to do is log in. You'll get a
response containing `client_id` and `client_secret`. Hang on to these. (This
happens in the `post-login` function.) The example code saves this in
memory, but realistically you would want to put this in a database.

Step 3: now that our client is registered we can do the normal flow. This
involves redirecting the user to the instance where they can log in. For
example, if the instance they gave is `yuri.camp` and the client ID was `602`
and your app's redirect URL was `https://echo.town/oauth` then send them to
`https://yuri.camp/oauth/authorize?client_id=602&redirect_uri=https://echo.town/oauth&response_type=code&scope=profile`.

Step 3.5: the user will probably need to log in. Mastodon will let you use an
existing login session if there is one, while GotoSocial will make you enter
your email/password regardless. Once they do that, they'll be asked if they
want to allow your app access to their profile. (This doesn't really count as
a step because it all happens outside your codebase.)

Step 4: the user will click the "allow" button, which will grant access and
redirect the user back to your `/oauth` endpoint. (the `oauth` function). The
query params will include a `code` which you'll need to exchange for a
token. Make a POST request to `https://yuri.camp/oauth/token` with
`client_id`, `client_secret`, and `redirect_uri` from earlier, the `code` we
just got, and `grant_type` of `"authorization_code"`. The JSON body you get
back will have an `access_token` field you'll need.

Step 5: you're so close you should be able taste it now. Make a GET call to
`https://yuri.camp/api/v1/accounts/verify_credentials` with the
`Authorization` header set to `"Bearer ACCESS_TOKEN"`. Boom; the JSON
document you get back will have a bunch of information about the user. Oddly
their `@someone@yuri.camp` style username will not be included, so you'll
need to either build that using the `username` field plus the instance
hostname, or use the `url` as the unique identifier. But you have
successfully verified the user's login, congratulations!
