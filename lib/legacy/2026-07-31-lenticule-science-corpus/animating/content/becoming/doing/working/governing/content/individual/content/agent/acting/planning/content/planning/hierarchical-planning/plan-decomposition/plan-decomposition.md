# Plan decomposition

**Plan decomposition** is the operation by which an abstract plan is refined into a more concrete plan by replacing compound tasks with their method-prescribed sub-task networks.
It is the core operator of HTN planning.

## The decomposition step

Let $w$ be a current task network and $\tau \in w$ a compound task.
Choose a method $m: \tau \mapsto \langle w_\tau, \mathrm{pre}(m) \rangle$ applicable in the current state (i.e., $\mathrm{pre}(m)$ holds).
The result of decomposing $\tau$ via $m$ is the network

$$w' = (w \setminus \{\tau\}) \cup w_\tau$$

with the partial-order constraints from $w$ extended to require that the tasks in $w_\tau$ occur where $\tau$ occurred (preserving any ordering constraints $\tau$ had with other tasks in $w$).

Repeated application of decomposition transforms an initial network of high-level tasks into a network of primitive actions: an executable plan.

## Choice points

Decomposition involves three choice points:

1. **Which compound task to decompose next** (when several remain).
  Often deferred via a most-constrained-first heuristic.
2. **Which method to apply** (when several are applicable to the chosen task).
  The principal source of branching in HTN search.
3. **How to order the resulting sub-tasks** (when the method's output network admits multiple linearizations).

The HTN search procedure backtracks over these choices, like classical search backtracks over action selection.

## Soundness

A decomposition step is *sound* if every executable plan reachable by continuing from $w'$ is also a valid solution had it been reachable from $w$.
The [hierarchical-decomposition-soundness](../theorems/hierarchical-decomposition-soundness.md) theorem gives the precise conditions under which the decomposition preserves classical-planning validity.

## Costs of decomposition

**Search-space pruning** (positive): a method library that captures domain knowledge dramatically prunes the search space relative to flat classical search.

**Restricted expressivity** (negative): plans not expressible by any method-application sequence are unfindable.
The library, not the underlying classical problem, defines what the planner can find.

**Decomposition as commitment** (negative): once a method is chosen for a task, the planner commits to the resulting sub-task network.
Backtracking over method choice is possible but expensive.

## In RL: the options framework

The RL analogue of plan decomposition is *option execution*: when the agent selects an option, it executes the option's policy until the option terminates, then resumes high-level decision-making.
This is decomposition-by-execution rather than decomposition-by-search: the option's "decomposition" is dynamically realized by its policy running in the environment.

## In LLM agents

LLM-based agentic systems perform implicit plan decomposition constantly: a high-level task ("plan a trip") is decomposed by the LLM into mid-level sub-tasks ("research destinations", "book flights", "book accommodation"), each of which is further decomposed when selected.
The decomposition is not generated from an explicit method library; it is generated by sampling from the LLM conditioned on the task and prior context.

This implicit decomposition has practical advantages (no manual library; broad coverage) and theoretical disadvantages (no soundness guarantees; failures opaque to debugging).
It is structurally the same operation as classical HTN decomposition; what differs is the decomposition rule's representation (model weights vs explicit methods) and verification status (none vs explicit precondition checking).
