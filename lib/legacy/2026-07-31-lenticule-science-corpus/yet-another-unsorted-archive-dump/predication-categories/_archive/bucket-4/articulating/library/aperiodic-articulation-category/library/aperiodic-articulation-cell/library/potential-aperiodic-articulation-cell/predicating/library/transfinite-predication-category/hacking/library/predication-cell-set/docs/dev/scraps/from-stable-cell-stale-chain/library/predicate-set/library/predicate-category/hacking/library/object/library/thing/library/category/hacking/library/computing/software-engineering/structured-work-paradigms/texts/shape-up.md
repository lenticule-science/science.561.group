Shape Up is a product development method created by Ryan Singer at
Basecamp (formerly 37signals). Singer compiled the method from
Basecamp's internal practices and published it in 2019 as *Shape Up:
Stop Running in Circles and Ship Work that Matters*, available free
online at basecamp.com/shapeup.

## Core concepts

Shape Up organizes work into three phases --- shaping, betting, and
building --- and structures time into six-week cycles followed by
two-week cool-down periods.

**Shaping** is the design work that happens before a project is
scheduled. Senior staff define the problem, sketch a solution at a
rough level of abstraction, and set boundaries. A shaped project has
three properties: it is rough (not a detailed spec), solved (the
main approach is clear), and bounded (the scope fits within the time
appetite).

**Appetites, not estimates.** Shape Up replaces estimation with
appetite-setting. An estimate starts with a design and ends with a
number; an appetite starts with a number and ends with a design. A
team decides how much time a problem is worth --- typically two weeks
(small batch) or six weeks (big batch) --- and shapes the scope to
fit within that budget.

**Betting** replaces prioritized backlogs. During the cool-down
period, a small group of decision-makers (at Basecamp: the CEO, CTO,
and a product strategist) meets at the "betting table." They review
pitches --- short documents describing a shaped project --- and
decide which to fund for the next cycle. Unselected pitches don't
carry over automatically; they must be re-pitched in a future cycle.

**Building** follows a circuit-breaker pattern. Teams get six weeks
to ship; if the work isn't done by the deadline, the project is
re-evaluated rather than extended. This prevents projects from
dragging on indefinitely.

## Planning mechanisms

Two tools structure visibility during the building phase:

**Scopes** divide a project into meaningful pieces that can be
completed independently. Unlike task lists, scopes are organized
around what the user experiences, not around technical layers.

**Hill charts** track progress within each scope. A hill chart is a
curve divided into two halves: uphill (figuring things out, resolving
unknowns) and downhill (executing known work). Team members drag dots
along the curve to show where each scope stands. The top of the hill
marks the point where all ambiguity is resolved.

The cool-down period between cycles serves multiple functions: it
absorbs schedule slack, provides time for bug fixes and small
improvements, and creates space for the betting table to meet without
competing with active project work.
