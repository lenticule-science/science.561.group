# relating/ — Infomaterial: instructions for future Claude

You are building **Infomaterial**, a dependency-free Lean 4 library that is the complete formalization of the 561 Group corpus math.
Read this before touching anything here.
The formal frontier and live claim graph are in the Blueprint under [docs/blueprint](docs/blueprint); read that too.

## What Infomaterial is

The corpus (`dev/content/`) is a **non-Western generative mathematics**: the directory path *is* a Curry–Howard proof, each segment generated by the one before it.
Received Western math (order theory, logic, category theory, topology, probability, linear logic, type theory) appears only as **derived comparisons or specializations** in-chain.
Infomaterial re-derives all of it in Lean, faithfully.

The spine descends through four base verbs — **articulating → predicating → positing → settling** — which **conflate at depth** (the same coherence cell recurs everywhere).
Each result also carries a **regime** signature: strict-finite (κ<ω) / Scott-continuous (κ=ω) / transfinite-bounded / aperiodic (κ≥ω₁).

## The one inviolable law: no free data

**Past `Mark` and `Articulating`, nothing is free.** Only those two modules admit primitives (the atomic mark; the articulating recursion).
Every other module *derives* its content.
So in any file other than `Mark.lean`/`Articulating.lean`:

- **No new primitives.** Never `axiom`, `opaque`, `constant`, or `native_decide` — these smuggle in free data or external trust.
  A *proved* result may depend only on the core logical axioms `propext` / `Quot.sound` (the latter is how `funext` enters); prefer zero.
  Verify a proved result with `#print axioms <thm>`.

## Proofs and the frontier (proved vs hypothesized)

A `sorry` is **not** free data — it is a missing *proof* of a still-derived statement, and Lean flags it loudly (`#print axioms` shows `sorryAx`).
So `sorry` is the honest marker of the frontier, allowed, under discipline:

- **If you can prove it, prove it.** Never `sorry` — or weaken — a result you have the context to discharge.
  Holes are for what you genuinely cannot prove yet, never a shortcut to "finish" a task.
- **State the real claim at full strength.** When you cannot yet prove it, write the real statement and leave the proof a `sorry` (or take the missing fact as an explicit hypothesis `(h : P) → …`).
  The frontier *is* the set of `sorry`s; you move it by filling them.
  This is how the project grows — not by deleting what isn't proved yet.
- **Never fake.** Do not define a target to equal what you already have and `rfl` the "equality"; do not weaken a statement to a triviality while the prose claims the strong thing.
  Overclaiming trivial Lean is the cardinal sin (see House style).
- **Proved means clean.** A result you export or mark `\leanok` (green) in the blueprint must be `sorry`-free and axiom-clean.
  Frontier `sorry`s stay openly unproven (red in the blueprint) until filled.

## Method (from the corpus discipline — obey it)

- **Read the indicated corpus node first.** When formalizing a structure, open its `content/.../<slug>/<slug>.md` (+ `references/`, `explanations/`, sometimes `_archive/`) and read it. **Never guess from a slug.** One read of the named file beats ten skimmed neighbours.
- **Derive, don't import.** A received-math result is a generated comparison or specialization of a settling-stage structure; place/derive it at the stage that generates it, not by topical resemblance. Reserve `shadow` for the formal d-frame shadow object in `Infomaterial.Site.DFrame`.
- **Absence is a design judgment.** If something expected is missing, find the new principled form — do not reconstruct/alias/stub the old one.
- The corpus's depth is real and past the public literature (and past training cutoffs).
  When a claim looks novel, it usually is — read, don't pattern-match.

## The keystone insight (the connective tissue to keep proving)

The four verbs are **one recurring four-corner coherence cell**: `{potential,active,stable,absurd}` (articulation) ≅ `{⊥,t,f,⊤}` (charge) ≅ `{free, j₁-fix, j₂-fix, both}` (nuclear quartet) ≅ `{neither,◇,□,both}` (modal) ≅ `{strict,Scott,TB,aperiodic}` (regime).
Infomaterial must make each conflation a **theorem**, not a comment.
`twistoring`-at-articulating = `commutating`-at-aperiodic-settling.
The keystone module is **QuartetRecurrence**; `FourCornerCell` is its first instance (`articulation_phase_is_charge`).

## House style

- **Bundled structures**: `structure Foo where carrier : Type; op : …; law : …`.
  Derive the order from the algebra (`le a b := meet a b = a`).
  See `OrderInfra.lean`, `BigradedDiamond.lean`, `ResiduatedLatticeStandalone.lean`.
- **Finite carriers** (`Charge` = `Corner`, `Bool`, `Two`): prove by exhaustion + `rfl`/`decide`. **`decide` cannot quantify over `Charge`/`Corner`** (no `Fintype`-∀ instance in core) — use `cases a <;> cases b <;> decide` (concrete per case), or make the relation `abbrev`/reducible so `decide` sees the underlying `Bool` equality (`KLE`/`TLE` are `abbrev … = true` for exactly this reason).
- **Namespaces**: everything under `namespace Infomaterial`; sub-namespaces `Order`, `Charge`, `Valuation` as appropriate.
  Don't collide names.
- **Docstrings are idiomatic and concise** (Mathlib style): `/-! … -/` module header stating the mathematics + a one-line corpus cite; `/-- … -/` on each declaration saying what it *is*. **No defensive boilerplate** — never write "No free data", "no `sorry`", "depends only on `propext`/`Quot.sound`", "HEADLINE", or "Honest scoping" in comments.
  Those properties are enforced by review and `#print axioms`, not advertised.
- **The module header MUST be `/-! … -/`, placed *after* the `import` lines.** Two non-obvious facts make this load-bearing: (1) only `/-!
  ` registers as a *module docstring* — a plain `/- … -/` header is stripped and is invisible to generated docs, Verso `{moduleDocs}`, and LSP hover, so the exposition exists but reaches no reader; (2) `/-!
  ` is a *command*, so it is a parse error before `import` ("invalid 'import' command").
  The Mathlib-legal shape is therefore: `import …` lines first, blank line, then `/-! # Title … -/`, then `namespace …`.
  (A header on a file with no imports may sit at the very top.)
  Headline modules earn the full Mathlib structure: `## Main definitions`, `## Main results`, `## Implementation notes`, `## References`, `## Tags`.
- **A statement claims exactly what the Lean proves — no more.** Do not define a target to equal what you already have and then "prove" the equality (`Derived := Čech` then `Iff.rfl`).
  If the genuine result is stronger than what you can prove, the *aspiration* belongs in the blueprint as a red (unproven) node with its `\uses` dependencies — that is what the blueprint is for.
  Overclaiming prose over trivial Lean is the cardinal sin here.
- **Naming follows the house style here and the Blueprint coverage rule** (topic = namespace, concept = module, term = theorem; a name claims only what is proved).
  The `iff`/`eq`-name-vs-statement-shape rule is enforced by `lake exe checknames` (in `make check`); honor the rest as review discipline.
- **No Mathlib, no external deps.** Lean core only; the lakefile has no `[[require]]`.

## The cockpit: do Lean with Lean (LSP-first, not the shell)

**For every Lean interaction, default to the `lean-lsp` MCP tools.
Do NOT shell out to `lake` / `grep` / `Read` for what the LSP answers directly** — that is slower, costs more tokens, and throws away the goal state.
The server should point at this directory as the Lean project root (`uvx lean-lsp-mcp --lean-project-path .`); `ripgrep` is on PATH so its search/scan work.

| You want to… | Use (LSP MCP tool) | NOT |
|---|---|---|
| a file's errors/warnings | `lean_diagnostic_messages` | `lake build` + read the log |
| confirm a decl exists / its axioms | `lean_verify` (fully-qualified name) | `grep` for the name |
| find a declaration by name | `lean_local_search` | `grep -r` |
| the proof state at a point | `lean_goal` (line[, col]) — *the* most useful tool | guessing |
| try tactics without editing the file | `lean_multi_attempt` | edit → rebuild → revert |
| a decl's signature + docstring | `lean_hover_info` | `Read` the file |
| a file's skeleton | `lean_file_outline` | `Read` the whole file |
| search math (Mathlib) | `lean_leansearch` / `lean_loogle` / `lean_leanfinder` | — |

- **Single-file work:** `lean_diagnostic_messages` restarts nothing and is near-instant — use it after each edit instead of `lake build`.
  Verify a headline with `lean_verify` (returns the axiom set; clean = `[]` or `[propext, Quot.sound]`).
- **Whole-project procedures stay shell, via the [Makefile](Makefile)** (not raw `lake`): `make build` (full library) and `make check` (build plus the local checknames honesty gate).
  A full `lake build` is the last-resort whole-tree check, not the per-edit loop.
- **The frontier pipeline (where math lives):** the corpus (`dev/content/`, incl.
  `_archive/`) is the far frontier — *what might be*, the generative source / "the paper."
  A result graduates to a **blueprint** node when precisely stateable: `\notready` (red = stated, unproven, near frontier) → `\leanok` (green = proved, `\lean{}` links the decl). **Verso** (`docs/verso/`) documents *what is*.
  So: speculation → corpus; precise open claim → blueprint red node; proved → blueprint green + Verso prose.
  Never let aspiration live as an overclaiming docstring — that is the cardinal sin above.

## Build & integrate

- **Every local tooling procedure is a `make` target — use the [Makefile](Makefile).**
  `make build` builds the library; `make check` builds it and runs the local naming gate.
  `make doctor` if something breaks.
  If a procedure is wrong, fix it in the Makefile so the fix is permanent.
- Build: `lake build` (or `make build`).
  Toolchain `leanprover/lean4:v4.31.0` (installed elan default).
  Root `Infomaterial.lean` imports every module **in dependency order** — add new imports there.

### Ultracode parallel-drafting pattern (when opted in)

Drafting independent modules scales well via worktree agents:

1. Pick modules whose deps are **all already built** and that don't depend on each other.
2. `Workflow` with one `agent(..., { isolation: 'worktree', schema })` per module. Give
   each: the module spec, the `content/` nodes to read, these conventions, and the
   existing-module API list. Each agent **reads the corpus, writes
   `Infomaterial/<M>.lean`, runs `lake build` + `#print axioms` in its worktree**, and
   returns the full source.
3. Integrate yourself: extract each `source` field from the task's `.output` JSON with a
   small `node -e` script (this keeps the generated Lean **out of your context**), write
   to `Infomaterial/`, add imports to `Infomaterial.lean` in dep order, run the **full**
   `lake build`, and re-verify the no-free-data invariant. Fix integration issues; if a
   module is wrong/unfaithful, redo it.

Solo (no ultracode): build one verified module per turn.
Same discipline.
