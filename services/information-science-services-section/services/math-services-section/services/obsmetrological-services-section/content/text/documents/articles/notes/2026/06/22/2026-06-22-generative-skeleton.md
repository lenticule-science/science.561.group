# The generative skeleton — RelMath as one Curry–Howard–Lambek language cone

The directory tree IS a proof.
Each folder is a **CHL language cone**: an apex (the generator) over the extrema it generates, the generative morphisms being the corpus's GENERATED-BY relation (`content/CLAUDE.md`: "which one must exist for the other to exist?").
Read a module path left-to-right and it is the Curry–Howard derivation of that concept.
The whole `RelMath/` tree is one cone with apex `Mark` and extrema the leaf applications.

## Three axes, decoupled (the key corrections)

* **Directory = the generative AREA, kept FLAT (one level).** A module lives in the top-level area that generates it — the apex-spine stages (`Articulating/`, `Predicating/`, `Positing/`) and the settling fan-out (`Order/`, `Closure/`, `Cohomology/`, `Aperiodic/`, `Flow/`, `Value/`, …).
  We do **not** deep-nest the fan-out under `Settling/`: that buys "path = proof" at the cost of `RelMath.
  Settling.
  Cohomology.
  Aperiodic.
  Classification` — a stupid-long namespace.
  The generative descent is fully recorded by the import DAG + this doc's generated-by annotations, so nesting it in the directory adds nothing and costs depth.
  Result: ≤ 3 namespace segments.
* **Namespace = the mathematical object / concept** (Lean-idiomatic, shallow, shared across files — `Valuation`, `Charge`, `Aperiodic`).
  Decoupled from the path, exactly as Mathlib does (`Mathlib/Order/Lattice.lean` → `namespace Lattice`).
  Preserves dot-notation and cohesion.
* **Module-path = directory + file** (`RelMath.
  Flow.
  ClosureFlowDynamics`) — appears only in `import` lines, so it can be a touch longer without polluting code.

Decoupling dissolves the topic-vs-object dilemma: closure-flow's *file* lives in `Flow/` (it is generated by settling's closure), while its declarations stay in `namespace Valuation` (so `v.driveFlow` works).
You place files by generator; decls live in their object namespace.

Placement authority is the corpus's generative story, with the Lean import DAG as a guide (imports may cross the flat areas — `Four` technically imports `TruthOrder`, but FOUR is *generated at positing*, so its file lives in `Positing/`).

## Instantiation order (leaf-first; the DAG is the safety rail)

Move **low-ripple leaves first**, heavily-imported **foundations last** (`Mark`, `Four`, `Settling`, `Sheaf`, `OrderInfra` — imported everywhere).
`lake build` catches a missed import; `checkdecls` catches a missed name (but with namespaces kept decoupled, decl names rarely move, so blueprint is usually untouched).
Recipe per cone: `mkdir RelMath/<Area>/`; `mv` its modules in; keep namespaces; `sed 's@^import RelMath\.<M>$@import RelMath.<Area>.<M>@'` over root + the moved files + any external importers (grep them first); `make check`.
The done areas (Aperiodic, Flow, Lorentzian, Probability, LinearAlgebra) are already top-level — no re-nesting needed.

## Why this is the long-term structure

Topic grouping files by resemblance; generator grouping files by derivation.
The payoff compounds: the path is the proof; generation-order = dependency-order = import-order, so the tree can't cycle; and every new result has a determined home — "what generates it" — not a junk-drawer guess.
It is the only filing rule that scales a re-founding of mathematics past Mathlib without entropy.
