# t02-30f — Admin-role authoring fixture (paired)

## Description

Per [decisions/fixture-authoring-paired-task.md](../../decisions/fixture-authoring-paired-task.md), every `t02-NN` task that ships normative substrate behaviour has a paired `t02-NNf` fixture-authoring task with its own conformance gate.
This is that pair for [t02-30](t02-30-v0.2a-multi-user-authoring.md) — the **admin-role slice** of the multi-user authoring surface.

The umbrella fixture [`test_t02_34f_multi_user_authoring.py`](../../../../tests/conformance/test_t02_34f_multi_user_authoring.py) already exercises admin → member → observer end-to-end against the role-default capability fibers from [`init_boot.bootstrap_users.
ROLE_CAPABILITIES`](../../../../src/init_boot/bootstrap_users.py); this paired fixture is the **per-role refinement** asked for by [t02-30](t02-30-v0.2a-multi-user-authoring.md)'s acceptance — admin authority alone, without entanglement with the member-retract or observer-deny legs.
The narrower scope makes the admin's capability fiber the single named hypothesis on test, so a future change that quietly weakens the admin role (or accidentally widens it past `signal:*` + `respond:*`) is the only thing that can break this fixture.

The fixture lives at `tests/conformance/test_t02_30f_admin_authoring.py` and witnesses the load-bearing acceptance items from [t02-30](t02-30-v0.2a-multi-user-authoring.md):

- *"`bootstrap_users` emits the admin role in the per-user capability fibers per `boot-sequence.md` §4.1"* — pinned by asserting the admin's persisted `granted:*` cells on the boundary entity match the §6.4 spec literal `{respond:*, shell:*, runlevel:*, audit:*, signal:*}` (not the runtime `ROLE_CAPABILITIES["admin"]` constant), and the four boundary-projection cells (`projects-auth-fiber`, `projects-authz-fiber`, `projects-attention-fiber`, `projects-history-fiber`) plus the `kind-user` and `role-admin` cells are all present at value `True` on the admin's `user:<slug>` entity per [decisions/identity-is-boundary-projection.md](../../decisions/identity-is-boundary-projection.md).
- *"the admin can assert any cell within its scope"* — the admin opens a session, asserts `(task:demo, status-open) = TRUE`, and the resulting fiber carries `TRUE` (no contradiction, no `Both`, no denial).
- *"a non-admin sender attempting the same `respond` is restricted by ⇒ to ⊥ at the cells the admin alone can write, with no event emitted"* — the gate-ordering invariant of [capability-permissions.md §6.3](../../specs/filesystem/capability-permissions.md): an observer-role session (whose role-default fiber carries no `signal:*` grant) attempting `set_current_scope` raises `PCA_SCOPE_INSUFFICIENT` and advances neither the event log nor any fiber.
  The cross-role positive-control case (member's `signal:session-scope:set` covering its own scope-set) lives in the umbrella [`test_t02_34f_multi_user_authoring.py`](../../../../tests/conformance/test_t02_34f_multi_user_authoring.py); this fixture isolates the admin slice and uses the observer as the negative-control foil.
- *"byte-identical fiber state across two runs"* — the admin slice is replayed against two fresh substrates with `process.session.secrets` monkeypatched to a deterministic counter; `events.jsonl` is byte-identical between runs.

The fixture's scope is **admin authority**, not the full three-role surface.
The umbrella `t02-34f` remains the cross-role conformance gate; this fixture is the regression fence for the admin slice in isolation.

## Acceptance

- The fixture file exists, is collected by pytest, and all four tests pass against the current implementation.
- The fixture exercises the spec's acceptance claims (admin role, four boundary-projection cells, admin-only `signal:*` surface, byte-identical replay), not just the implementation's incidental behaviour, per [decisions/fixture-authoring-paired-task.md](../../decisions/fixture-authoring-paired-task.md) §"Why".
