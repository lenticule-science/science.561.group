# Goal: v0.3 userland is daily-driver-ready

## Outcome

The bundled userland (mail, calendar, chat, file browser, text editor, terminal, calculator, ledger) is sufficient that the captain accomplishes one daily task end-to-end through the OS that the previous version could not support.

## Acceptance

The nine-item conformance gate of [milestones/v0.3-bundled-userland.md](../milestones/v0.3-bundled-userland.md) §"Conformance gate" is satisfied.

## Decomposition

When v0.3 activates, this coarse goal SHOULD be replaced by per-app goals (email, calendar, chat, file browser, text editor, terminal, calculator, ledger, inbox UI, streaming-output UI) matching the milestone's scope sections.
The procedural template for each per-app goal is in [implementation/next-stretch.md §3B](../implementation/next-stretch.md#3b-first-bundled-apps-as-driver--verb--dashboard-tuples).

Row 13 of [theory-for-developers.md](../references/theory-for-developers.md) (self-representation) plus [`predicated-computing/theorems/doctrine-fidelity-via-faithful-interfacer-functor`](../../../../../../../../theories/engineering/theories/tech/theories/computing/theories/predicated-computing/theorems/doctrine-fidelity-via-faithful-interfacer-functor.md).

## Theory-derived per-app priority

The captain's daily-driver gate (gate 7 of v0.3) is closed by *any one* end-to-end workflow.
The cheapest first end-to-end is **terminal + calculator + ledger**: terminal is a thin wrapper over `repl.py` from v0.2b §2C; calculator's verbs are arithmetic specialisations of the message language; ledger reuses the hledger driver from v0.2b §2A.
Email and chat are heaviest (network, external protocol surface) and should land last.

Suggested per-app order: terminal → calculator → file browser → text editor → ledger → calendar → chat → email.
The inbox panel and streaming-output panel (gates 8 and 9) attach to whichever app lands first.

## Procedural steps (per app, applied N times)

Per [next-stretch.md §3B](../implementation/next-stretch.md#3b-first-bundled-apps-as-driver--verb--dashboard-tuples):

1. Author the app's spec under [specs/bundled-apps/<app>.md](../specs/bundled-apps/) naming: the driver (from v0.2b §2A's catalog), the verb extensions (under [specs/stdlib/](../specs/stdlib/) per v0.2b §2C), the dashboard view (per v0.2b §2B), the per-app conformance vector.
2. Author the (driver-cell + app-cell) pair as substrate content.
  The app-cell's `kind: app` predications point at the driver, the verbs, the view, and the package-record.
3. Per-app paired fixtures: a fixture for the app's primary user-visible workflow that round-trips through the driver and renders on the dashboard.

## Enables next

v0.4 federation between two captains' substrates can assume each substrate is *the substrate it claims to be* (3A's witness chain) and has *content* worth federating (the apps from 3B).
A federated calendar invite, a federated chat thread, a cross-node ledger reconciliation — none are even specifiable until v0.3 closes.
