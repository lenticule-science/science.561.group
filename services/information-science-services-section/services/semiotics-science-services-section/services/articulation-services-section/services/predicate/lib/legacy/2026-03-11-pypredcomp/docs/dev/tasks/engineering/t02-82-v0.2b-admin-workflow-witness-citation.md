## Grounding

Theory row 8 (capability/authz as modal restriction) of [references/theory-for-developers.md](../../references/theory-for-developers.md).
Admin is the *governance side of $\Box_R$* at the personnel/capability sub-region; the witnesses are the rejection trail.
Without a cross-cutting witness-citation discipline, each admin spec re-derives the witness-lifecycle in copy-paste-with-edits style.
Library grounding:

- [`witness-lifecycle-trajectory-is-regime-conditional-federation-content`](../../../../../../../../../theories/engineering/theories/tech/theories/computing/theories/predicated-computing/theorems/witness-lifecycle-trajectory-is-regime-conditional-federation-content.md) — the witness lifecycle IS regime-conditional; the spec must name the regime per workflow.
- [`witness-as-cell`](../../../../../../../../../theories/engineering/theories/tech/theories/computing/theories/predicated-computing/theorems/witness-as-cell.md) — every witness is a substrate cell; the per-class `kind` set declares the cell-shape contract.
- [`signature-binds-witness-to-identity`](../../../../../../../../../theories/engineering/theories/tech/theories/computing/theories/predicated-computing/theorems/signature-binds-witness-to-identity.md) — admin witnesses bind to admin identity; cite this for audit.
- Round-4 [`_patterns/witness-lifecycle.md`](../../specs/_patterns/witness-lifecycle.md) is the authoritative lifecycle pattern.

## Description

Round-4 §1.1 named the *admin-action-as-witness-emitter* discipline: every admin action produces a witness per the conformance gate, but the *class* of the witness is not unified across the five admin workflows.
This task ensures, when each admin spec is authored at v0.2b, that the witness-lifecycle pattern is cited and the per-class kind set is named explicitly.

**What this consumes from v0.2a + v0.2b.**

- v0.2a `t02-30`/`t02-31`/`t02-32` (multi-user authoring) supplies the personnel boundary entity each admin action targets.
- v0.2a `t02-40`/`t02-41` (settled capability + authz fibers) supplies the capability-grant/revoke primitive admin witnesses emit against.
- v0.2b `t02-50`/`t02-53` (driver model) supplies the driver-config-ui witness shape (drivers ARE substrate entities per [decisions/drivers-are-substrate-entities](../../decisions/drivers-are-substrate-entities.md), so driver-config witnesses are substrate cells).

**Spec citations.**

- Pattern: [`specs/_patterns/witness-lifecycle.md`](../../specs/_patterns/witness-lifecycle.md).
- Authorization model: [decisions/authorization-is-modal-restriction](../../decisions/authorization-is-modal-restriction.md).
- Identity: [decisions/identity-is-boundary-projection](../../decisions/identity-is-boundary-projection.md).

**Modules to touch.** Each per-admin-workflow spec under `specs/admin/` gains: (a) explicit citation of `_patterns/witness-lifecycle.md`; (b) per-class `kind` set declaration (typically a subset of `{capability-grant, capability-revoke, federation-trust, driver-config}`); (c) instantiation of the four-state lifecycle (`pending → emitted → acknowledged → archived`) without re-specifying the state machine.

**Procedure.** Follow [implementation/workflows.md recipe 10](../../implementation/workflows.md#10-promoting-a-thin-t02-nn-task-record-into-a-procedural-plan).
For each admin spec: (1) read the existing draft; (2) add the citation block at the top; (3) declare the kind set; (4) cite `_patterns/witness-lifecycle.md` for the lifecycle; (5) update conformance-vector backlog B1/B2/B3.

**Ship-target role.** Pre-condition for the v0.2b admin-spec normative gate.
Without this discipline, the five admin specs would produce five subtly different witness shapes that fail to compose at audit time.

**Depends on.** None.
Coordinates with [`task:t02-83`](t02-83-v0.2b-pattern-cross-citation-discipline.md) (which generalises this pattern-citation discipline to all per-pattern files).
