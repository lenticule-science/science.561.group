# t02-32 — Multi-user authoring (observer role)

## Description

Observer-role authoring slice for the multi-user authoring goal: ship the read-only observer capability fiber per the boundary-projection identity scheme.
The observer is the most-restricted of the three v0.2a roles; an observer's `respond` produces no state-mutating event — every payload restricts to $\bot$ in Phase 2 because the observer's authz fiber says nothing about authoring.
Read paths (`/cell/`, `/fiber/`, `query`) succeed under the attention fiber.

This role is the proof that capability non-amplification (row 8 of [references/theory-for-developers.md](../../references/theory-for-developers.md)) is structural rather than enforced by guard clauses: the observer cannot author *because the algebra forbids it*, not because a Python `if observer: raise`.
There is no "read-only mode" code path; there is only a fiber that is empty in the authz dimension.

**Spec citations.**

- Boundary-projection identity per [decisions/identity-is-boundary-projection.md](../../decisions/identity-is-boundary-projection.md).
- Capability model per [specs/security/capability-model.md](../../specs/security/capability-model.md); modal-restriction per [decisions/authorization-is-modal-restriction.md](../../decisions/authorization-is-modal-restriction.md).
  The observer's authz fiber is the empty fiber in the authoring dimension; the attention fiber is non-empty in the read dimension.
- User-as-boundary per [specs/security/user-as-boundary.md](../../specs/security/user-as-boundary.md).
- Multi-regime session discipline per [specs/process/multi-regime-session.md](../../specs/process/multi-regime-session.md).
- Theory grounding: row 8 of [references/theory-for-developers.md](../../references/theory-for-developers.md).
  Also relevant: row 1 (bilattice value domain) — the observer's restricted payloads do not become "errors"; they become $\bot$, and $\bot$ is first-class.
