# t02-31 — Multi-user authoring (member role)

## Description

Member-role authoring slice for the multi-user authoring goal: ship the member capability fiber and the member-only `respond` paths per the boundary-projection identity scheme.
The member role is the middle-permissive of the three v0.2a roles (admin / member / observer); landing it after admin (`t02-30`) narrows the capability-fiber discipline that admin established.

A member can `respond` against cells in entities the member is bound to; can retract its own prior cells; cannot grant authority to other users; cannot read other users' history-fiber cells.
The retraction path is the load-bearing thing — admin can retract anything, observer cannot retract at all, member can retract its own.
This is exactly where the per-stratum capability fiber for retraction (`pt-02` → `t02-126`) becomes visible.

**Spec citations.**

- Boundary-projection identity per [decisions/identity-is-boundary-projection.md](../../decisions/identity-is-boundary-projection.md) — each user is a boundary entity that projects four fibers (auth, authz, attention, history).
- Capability model per [specs/security/capability-model.md](../../specs/security/capability-model.md); modal-restriction per [decisions/authorization-is-modal-restriction.md](../../decisions/authorization-is-modal-restriction.md).
- User-as-boundary per [specs/security/user-as-boundary.md](../../specs/security/user-as-boundary.md) — the v0.2 minimum user record (slug + token-hash + scope strings).
- Multi-regime session discipline per [specs/process/multi-regime-session.md](../../specs/process/multi-regime-session.md) — the regime envelope governs what cells the member's `respond` may admit.
- Theory grounding: row 8 of [references/theory-for-developers.md](../../references/theory-for-developers.md) (capability and authorisation as modal restriction).
  Capability non-amplification is structural — the member algebra cannot grant authority it does not hold.

**Modules to touch** (proposed; confirm exact file boundaries with captain when picking up).

- [`src/process/user.py`](../../../../src/process/user.py) — boundary entity for the member user; capability scope strings restricted relative to admin.

  The Phase-2 restriction MUST drop cells the member's fiber says nothing about to $\bot$ (no event emitted), per row 8.
- [`src/init_boot/bootstrap_users.py`](../../../../src/init_boot/bootstrap_users.py) — emit the member role per [boot-sequence.md §4.1](../../specs/init-boot/boot-sequence.md).
  The bootstrap routine already supports per-role grants (see the existing `role-<role>` and `granted:<cap>` cell emissions in the module's docstring); confirm the member's grant set against the captain.
- [`tests/conformance/`](../../../../tests/conformance/) — member-asserts + member-retracts conformance test (paired with `t02-31f`).
  The existing [`test_t02_34f_multi_user_authoring.py`](../../../../tests/conformance/test_t02_34f_multi_user_authoring.py) is the umbrella; `t02-31f` is the per-role slice.
