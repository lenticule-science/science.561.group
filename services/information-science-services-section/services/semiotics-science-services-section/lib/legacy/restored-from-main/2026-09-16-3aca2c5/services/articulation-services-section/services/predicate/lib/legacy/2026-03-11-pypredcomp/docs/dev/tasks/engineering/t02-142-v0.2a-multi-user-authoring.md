## Description

Spec and pin the **bootstrap-user manifest** file shape: location on disk, JSON schema, canonical-form rules, hashing recipe.
The manifest hash determines whether a re-boot is a no-op (`t02-141`) or a delta — so the canonical form has to be deterministic across implementations (Python and Rust, byte-identical) per [specs/kernel/canonicalization.md](../../specs/kernel/canonicalization.md).

The bootstrap routine ([`src/init_boot/bootstrap_users.py`](../../../../src/init_boot/bootstrap_users.py)) currently consumes a manifest passed via the boot harness; this task records the canonical schema in `specs/init-boot/` (a new file or an addendum to `boot-sequence.md`), wires the schema into [`src/init_boot/boot.py`](../../../../src/init_boot/boot.py), and authors the conformance fixture that pins the byte-form.

**Spec citations.**

- [specs/init-boot/boot-sequence.md §4.1](../../specs/init-boot/boot-sequence.md) — the four-step bootstrap routine; this task adds the manifest-schema sub-section.
- [specs/kernel/canonicalization.md](../../specs/kernel/canonicalization.md) — the manifest's canonical-byte form is the same canonicalization the substrate uses for cells and events.
- [decisions/canonical-json-conventions.md](../../decisions/canonical-json-conventions.md) — lexicographic key sort, no whitespace, minimal numeric form.
- [decisions/content-hash-via-sha256.md](../../decisions/content-hash-via-sha256.md) — the manifest hash is SHA-256 of the canonical bytes.
- Theory grounding: row 3 (predication cell and content addressing) of [references/theory-for-developers.md](../../references/theory-for-developers.md).
  The manifest is structurally a content-addressed input to boot.

**Modules to touch** (proposed; confirm exact file boundaries with captain when picking up).

- A new spec file `specs/init-boot/bootstrap-manifest.md` (or an addendum to `boot-sequence.md` §4.1) — pin the schema, the canonical form, the hashing recipe.
- [`src/init_boot/bootstrap_users.py`](../../../../src/init_boot/bootstrap_users.py) — confirm the manifest hash computed by the routine matches the spec exactly; cite the new spec in the docstring.
- [`src/init_boot/boot.py`](../../../../src/init_boot/boot.py) — the boot harness loads the manifest from the configured path; cite the spec.
- A pydantic model for the manifest entry (likely in [`src/init_boot/bootstrap_users.py`](../../../../src/init_boot/bootstrap_users.py) or a new `src/init_boot/manifest.py`) per [implementation/python.md "What the Python implementation MUST NOT do"](../../implementation/python.md) — the model MUST round-trip canonical-JSON byte-identically.
- [`tests/conformance/`](../../../../tests/conformance/) — manifest canonicalization conformance test (paired with `t02-142f`).

**Procedure.** Follow [implementation/workflows.md recipe 1](../../implementation/workflows.md#1-landing-a-v02a-task-end-to-end).
Pay attention to recipe 7 step 4 (canonicalization round-trip) — the manifest pydantic model must round-trip canonical-JSON byte-identically, or the manifest hash will diverge across implementations.

**Ship-target role.** Contributes to gate item 3 of [milestones/v0.2a-multi-user-single-node.md §Ship targets](../../milestones/v0.2a-multi-user-single-node.md).
The manifest schema is the input contract; without a settled schema, idempotence (`t02-141`) is undefined.

**Depends on.** None directly; coordinates with `t02-141` (idempotence depends on a stable manifest hash) and `t02-140` (the routine consumes the manifest).
