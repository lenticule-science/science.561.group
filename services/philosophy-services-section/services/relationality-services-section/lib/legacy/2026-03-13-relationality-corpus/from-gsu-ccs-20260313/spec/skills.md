A **skill** is a modular, reusable capability that an agent discovers and loads on
demand. Skills follow the [Agent Skills open standard](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)
(released December 2025, adopted across Claude Code, Cursor, Copilot, Gemini CLI,
VS Code, and others). A skill is a file — or a directory containing a `SKILL.md`
— with YAML frontmatter that an agent can discover and invoke.

**Skills are the judgment layer.** A skill contains the instructions for *what the
LLM should reason about* in a step. The execution structure around that step —
sequencing, looping, I/O between steps — lives in a [Runbook](runbook.md).

## Progressive disclosure

Agents pre-load only the `description` field of every installed skill at startup.
This is the first disclosure level: enough to know *when* a skill applies without
loading its full content. When the agent decides a skill is relevant, it loads the
full body. Skills with long bodies therefore cost nothing until invoked.

This is why `description` must be self-contained and precise. It is the selector,
not a summary.

## Four types

Every skill is exactly one of four types, corresponding to the four positions in a
nuclear quartet ([NuclearQuartetSubalgebra](../math/nuclear-quartet-subalgebra.md))
generated by two commuting nuclei: σ (meaning-closure) and Δ (execution-closure).

**Process** — Fix(σ) ∩ Fix(Δ). Both meaning and execution fully closed. A numbered
list of instructions with no conditions. No `if` may appear. The same input always
produces the same output. In a runbook, a Process skill is the `system_prompt` for
a deterministic `llm-call` step — or replaces the LLM call entirely with a `script`
step.

**Procedure** — Fix(σ), not Fix(Δ). Meaning settled; execution path not yet
determined. A branching map that runs only long enough to produce a named output.
Every branch ends in a call to a named skill or a halt. No inline work: if a branch
contains instructions, extract them into a Process. In a runbook, a Procedure skill
drives a `conditional` step that selects which next step to run.

**Derivation** — Fix(Δ), not Fix(σ). Inference rules fully determined; the meaning
of the output is what is being produced. Applies enumerated rules to produce a
judgment — a named, typed output that classifies or assesses its input. No
control-flow branching. In a runbook, a Derivation skill is the `system_prompt` for
a typed `llm-call` step with a declared `result_type`.

**Inquiry** — Raw A. Neither meaning nor execution rules settled. Explores unknown
territory without a predetermined output shape. May loop, backtrack, or spawn skills
of any type. In a runbook, an Inquiry skill drives an open-ended `llm-call` step or
a loop with a convergence condition.

## Why exactly four

The nuclear quartet theorem (§nuclear-quartet-theorem) proves that two commuting
nuclei on an algebra produce exactly four canonical sub-algebras and no fifth.
Commutativity (σ∘Δ = Δ∘σ) is the hinge: without it the composite is not a nucleus
and the intersection Fix(σ)∩Fix(Δ) is not canonically defined.

You can arrive at a Process either by settling meaning first (Inquiry → Procedure →
Process) or by establishing inference rules first (Inquiry → Derivation → Process).
Both paths commute to the same place.

## Skills and runbooks

A runbook's `llm-call` step has a `system_prompt` field that is either inline text
or a path to a skill file loaded at runtime. This means:

- **A skill is reusable across runbooks** — the same judgment appears in multiple
  workflows without duplication.
- **A runbook composes skills** — complex workflows are YAML structure + skill calls,
  not monolithic prose.
- **Skills stay prose; runbooks provide structure** — skills do not need to describe
  their own sequencing; that is the runbook's job.

The migration path: write a skill first (understand what judgment is needed), then
write a runbook that calls it within a larger structure.

## Required frontmatter

Every skill MUST have YAML frontmatter with at minimum:

```yaml
---
description: "Does X to Y. Use when Z."
skill-closure-kind: process   # or: procedure, derivation, inquiry
---
```

`description` is a two-sentence string:
- Sentence 1 — what the skill does to what.
- Sentence 2 — when to use it: the condition that makes this skill the right choice.

`skill-closure-kind` is this repo's extension of the Agent Skills standard, declaring
the nuclear quartet type. It is the single source of truth for the skill's type.

A skill that needs supporting files (scripts, templates, config) MUST become a
directory containing a `SKILL.md` file plus those resources.

## Improvement skills

An improvement skill advances the state of a department. It MUST read the department's `PLANS.md` before deciding what to work on — the plan is the skill's
teleology. An improvement skill without a plan is operating blind.

## Naming and location

Name a skill by its output — see `spec/name.md` for the full naming rules.

Skills live as close to their content as possible:
- `skills/` — any agent in the repo might need this
- `spec/skills/` — agents working on spec content
- `math/skills/` — agents working on math content
- A skill directory sits at the same level as its corresponding `skills/` folder
