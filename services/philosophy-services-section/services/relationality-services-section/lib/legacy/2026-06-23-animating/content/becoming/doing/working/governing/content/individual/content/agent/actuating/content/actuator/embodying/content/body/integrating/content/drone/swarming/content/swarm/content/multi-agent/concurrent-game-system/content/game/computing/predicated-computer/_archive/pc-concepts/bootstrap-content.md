# Bootstrap content

The substrate's *minimum content list* a fresh substrate must admit before it can serve any operation. In the substrate's hyperdoctrine setting, bootstrap content is not arbitrary configuration — it is *the structurally-minimal substrate predications such that the substrate's [predication fibration](../../../../../../../humanities/theories/math/theories/categories/theories/predication-categories/objects/predication-fibration.md) is non-degenerate at $\bot$*. Per [bootstrap-determinism](../theorems/bootstrap-determinism.md), two substrates admitting the same bootstrap content (same canonical-JSON, same admission order) end up at byte-identical post-bootstrap state.

[bootstrap.md](bootstrap.md) describes the bootstrap *discipline* — that the substrate starts empty and is brought into operating state by ordinary messages. This concept fixes *what* those messages must contain so that the substrate becomes operational rather than merely populated.

## Why this concept exists

Without a fixed bootstrap content list, two implementations could "boot" with arbitrarily different starting state — same engine, different post-bootstrap behavior. The substrate's audit and federation disciplines depend on bootstrap state being reproducible across hosts; per [bootstrap-determinism](../theorems/bootstrap-determinism.md), this requires a fixed content list.

The list is *minimum* — additional content can be added by any particular substrate (specific apps, custom vocabularies). The list is the substrate-level baseline.

## The minimum bootstrap content list

A conformant substrate must admit, in order, the following content classes during bootstrap:

### 1. Self-identity establishment

The first message asserts the substrate's [identity-record](../objects/identity-record.md):

```json
{
  "kind": "identity-record",
  "substrate-id": "<canonical hash of this content>",
  "public-key": {
    "scheme": "Ed25519",
    "value": "<base64 of public key bytes>"
  },
  "name": "<human-readable name>",
  "creation-time": "<ISO 8601 UTC timestamp>"
}
```

Per [identity-key-custody](identity-key-custody.md), the corresponding private key is generated by the host at the same moment and stored in the chosen custody mechanism. Per [signature-binds-witness-to-identity](../theorems/signature-binds-witness-to-identity.md), the substrate's first signed witness is the bootstrap-attestation message proving the keypair is functional.

### 2. Value-domain attestation

A predication asserting which [bilattice-operation-table](bilattice-operation-table.md) the substrate uses:

```json
{
  "kind": "value-domain",
  "domain": "FOUR-v1",
  "operation-table-hash": "<hex-sha256 of the operation table spec>"
}
```

Per [bilattice-operation-table-correctness](../theorems/bilattice-operation-table-correctness.md), implementations using a different table are not running the same value domain. Per [conformance-via-fiber-algebra-functor](../theorems/conformance-via-fiber-algebra-functor.md), the value-domain attestation is what the substrate's federation handshake checks.

### 3. Canonical-form attestation

A predication asserting the substrate's canonical-form discipline:

```json
{
  "kind": "canonical-form-spec",
  "discipline": "canonical-json-v1",
  "spec-hash": "<hex-sha256 of the canonical-form spec>"
}
```

Per [canonical-form-via-settling-quiescence](../theorems/canonical-form-via-settling-quiescence.md), the canonical-form is the substrate-side enumeration of the Priestley dual; per [hash-injectivity-under-canonical-form](../theorems/hash-injectivity-under-canonical-form.md), implementations using different forms produce different hashes.

### 4. Initial closure-rule system

The substrate's first closure rules. Per [closure-rule-wire-format](closure-rule-wire-format.md), each is admitted as a closure-rule message. The minimum bootstrap rule set typically includes:

- **Settling-monotonicity rules.** Rules that ensure $\leq_k$-monotonicity of the substrate's value-domain.
- **Identity-record validation rules.** Rules that check identity-record well-formedness.
- **Federation-envelope validation rules.** Rules that check federation envelopes per [federation-envelope](federation-envelope.md).
- **Repair-catalog entries.** Rules per [repair](repair.md) for handling $\top$-cells.

A substrate without these baseline rules cannot validate its own incoming content; per [doctrine-fidelity-via-faithful-interfacer-functor](../theorems/doctrine-fidelity-via-faithful-interfacer-functor.md), validation rules are the structural form of the substrate's interfacer faithfulness.

### 5. Initial vocabulary

The substrate's first predicates. Per [vocabulary-completeness](vocabulary-completeness.md), the vocabulary determines what claims are admissible. The minimum bootstrap vocabulary includes:

- **Built-in predicates** — `succeeds-key`, `revokes-key`, `closure-rule-of`, `is-recipient-of`, etc. — predicates the substrate's own machinery uses.
- **Federation-graph predicates** — `is-peer`, `routes-to`, `signs-with`, etc. — predicates for the federation discipline.
- **Vocabulary-completeness predicates** — `vocabulary-version`, `predicate-defined`, etc. — predicates for tracking the vocabulary itself.

### 6. Bootstrap-attestation witness

The substrate's first signed witness, recording that bootstrap completed successfully:

```json
{
  "kind": "bootstrap-attestation",
  "substrate-id": "<the substrate's id>",
  "bootstrap-content-hash": "<hex-sha256 of all preceding bootstrap messages>",
  "completion-time": "<ISO 8601 UTC timestamp>",
  "signature": {
    "scheme": "Ed25519",
    "signing-key-hash": "<hex-sha256 of public key>",
    "value": "<base64 of signature>"
  }
}
```

Per [witness-chain-as-proof-object](../theorems/witness-chain-as-proof-object.md), the bootstrap-attestation is the substrate's proof object that bootstrap occurred — replayable, verifiable, audit-traceable.

## Bootstrap admission order

The order matters. Per [bootstrap-determinism](../theorems/bootstrap-determinism.md), two substrates admitting the same content in the same order produce byte-identical post-bootstrap state. Out-of-order admission may produce different state (e.g., admitting closure rules before the value-domain spec is set leaves the rules in an undefined value-domain).

The canonical order:

1. Self-identity (substrate exists).
2. Value-domain attestation (operations are defined).
3. Canonical-form attestation (serialization is defined).
4. Closure-rule system (validation is defined).
5. Initial vocabulary (predicates are defined).
6. Bootstrap-attestation witness (bootstrap completed).

After step 6, the substrate is operational. Subsequent admissions are ordinary substrate operations.

## What additional bootstrap content typically follows

The minimum is the substrate-level baseline. Particular substrates typically add:

- **Application-specific vocabularies** (per the [interactive-application-platform](theories/interactive-application-platform/) sub-theory: account, document, list, form schemas).
- **Application-specific closure rules** (validation, derivation, propagation rules for each application).
- **Federation-graph entries** (per [federation-graph](theories/agential-orchestration-platform/objects/federation-graph.md): initial peers, bridges, routing).
- **Governance configuration** (per [governance](theories/agential-orchestration-platform/concepts/governance.md): initial offices, authority assignments, repair catalog entries).
- **Scope structure** (per [scope](scope.md): initial scopes, sublocale projections, application sublocales).

These are deployment-specific; the substrate-level baseline above is what every conformant substrate must include.

## What the spec rules out

- **Substrates with no identity.** A substrate without a self-identity cannot sign witnesses; per [signature-binds-witness-to-identity](../theorems/signature-binds-witness-to-identity.md), this breaks attribution. The substrate refuses to enter operational state.
- **Substrates with mismatched value-domains.** A substrate whose value-domain attestation differs from the substrate's actual implementation is non-conformant; per [conformance-via-fiber-algebra-functor](../theorems/conformance-via-fiber-algebra-functor.md), conformance fails on the value-domain layer.
- **Substrates without closure-rule validation.** A substrate that admits content without validating against the bootstrap closure rules cannot enforce its own discipline. The substrate's discipline is to defer admission until bootstrap closure rules are in place.
- **Substrates with mid-bootstrap operation.** A substrate that begins serving operations before bootstrap-attestation is signed is in an indeterminate state; per [bootstrap-determinism](../theorems/bootstrap-determinism.md), the bootstrap-attestation is what marks operational readiness.

## Position

Bootstrap content is the substrate's *operational-readiness floor*. Per [bootstrap-determinism](../theorems/bootstrap-determinism.md), two substrates with the same bootstrap content reach the same post-bootstrap state, enabling federation and audit equivalence from the moment of operational readiness.

The concept composes with [bootstrap](bootstrap.md) (the discipline of "starts empty, brought up by messages"), with [identity-key-custody](identity-key-custody.md) (the keypair custody discipline that supports the identity-record), with [federation-envelope](federation-envelope.md) (the envelope spec the bootstrap closure rules validate), and with [vocabulary-completeness](vocabulary-completeness.md) (the discipline of admitting predicates explicitly).
