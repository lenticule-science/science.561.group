A design pattern for wiring the "acts" vocabulary (Recognition, Witness, Trace, Judgement, Seed-Observation, Normalize-Observation, and the rest of this section's constructor family) into an executable pipeline, recovered from an unbuildable Python prototype (a FastAPI-shaped app with a `runbooks/` YAML directory, an `app/rewriter/` package, and MCP-server hooks). The prototype never compiled — it has no `requirements.txt`/`pyproject.toml`, several of its own internal imports point at modules that don't exist in the snapshot, and every act-implementing function found was an explicit placeholder returning a canned success value regardless of input. What survives that is worth keeping is the **shape** of the pipeline, not any of its code.

## The pattern

- **A runbook is a YAML document naming a sequence of steps, each step referencing one or more acts by slug.** A step cannot exist without at least one act reference — this is the mechanism that keeps every operation formally justified and traceable back to the section's own act vocabulary, rather than letting ad hoc application logic accumulate uncited.
- **Steps declare typed inputs and outputs, and wire them explicitly.** An input can either come from the runbook's own external payload or `from_step: other_step.output_name`, naming exactly which prior step's output it consumes. There is no implicit shared state between steps.
- **Dependencies are declared, not inferred from wiring.** Each step lists `depends_on: [...]` explicitly; the intent is that an execution engine builds a dependency graph from these declarations, rejects cycles, and then executes independent steps in parallel while respecting the declared order — the wiring (`from_step`) and the dependency graph (`depends_on`) are two separate declarations that must agree, rather than one being derived from the other.
- **A runbook can declare `policy_requirements`: named policies that must be satisfied before execution is allowed to start.** This separates "is this runbook allowed to run at all" from the per-step logic itself.
- **Each act slug is backed by a handler, registered once, looked up by act name at execution time.** The intended registration path was a `HandlerRegistry` matching each act to the Python class implementing it (`class MyActHandler(ActHandler): acts = [...]`) — i.e. the runbook YAML is pure declaration, and the mapping from act-slug to actual executable behavior lives in exactly one place, not scattered per-runbook.
- **The same runbook definition is meant to be reachable three ways**: a REST API (`POST /runbooks`, `/runbooks/validate`, `/runbooks/{id}/execute`), and an MCP server surface (`list_runbooks`, `validate_runbook`, `execute_runbook`) exposing the identical operations to an agent rather than a human client. Validation is a first-class operation distinct from execution — a runbook can be checked for well-formedness (every step's acts exist, the dependency graph has no cycles, every `from_step` reference resolves) without being run.

## Status

This is a recovered design description, not verified or tested code. The prototype it comes from cannot be built or imported as-is: several files reference sibling modules (`relationality.validation`, `relationality.models`, `app.rewriter._temporal_modality_common`) that do not exist anywhere in the snapshot, and every act-implementing function actually present (`reach_limit`, `reach_measure`, `sound_syntax`, `substitution`, and others) is an explicit placeholder that returns a fixed "pass" result irrespective of its arguments. The prototype's own `runbooks/README.md` documents example runbooks and a `builtin_handlers.py` that are not present in the snapshot either — the documentation describes a more complete system than what was ever committed.

The one part of the prototype that is real and concrete is the runbook YAML shape itself (`depends_on` graphs, `from_step` wiring, typed `inputs`/`outputs`, `policy_requirements`) — more fully specified than anything else in this section's existing "ideas for concept computers" catalog of hypothetical relational-computer subsystems. If this pattern is built for real, it belongs in this section's own typed-carrier idiom (`@red-cup-engineering/computer-data-type-engine`), with the handler registry and dependency-graph execution as an `admit`-checked pipeline rather than untyped Python dicts standing in for evidence.
